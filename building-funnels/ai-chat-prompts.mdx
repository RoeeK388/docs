A useful Jurni prompt tells the assistant **what to change, what to use, what to preserve, and how you will check the result**. More words are not automatically better: precise scope is more useful than a long list of vague improvements.

## Use this prompt structure

```text
Goal: What should the page or section achieve?
Target: Which page, section, or element should change?
Reference: Which product, ad, Figma frame, web page, or approved copy should be used?
Change: What should be different?
Preserve: What must remain unchanged?
Check: What should be true when the work is finished?
```

You do not need every label for a small edit. “In the selected FAQ section, change only the second answer to the approved copy below” is already a clear request.

## Match the prompt to the stage of the build

For a new page, describe the audience, traffic source, product, goal, and reference. For a nearly finished page, narrow the task to one section or one behavior. Avoid asking for an entire redesign when the problem is one image crop or spacing value.

Bring real product and media context into the chat using the available attachments. For a Figma reference, include both desktop and mobile frame links and label them. For a web reference, say whether to use its appearance, shopping interaction, copy structure, or a combination.

## Separate design, content, and purchasing logic

A screenshot shows appearance, not the implementation of variants, subscriptions, discounts, or cart actions. State those behaviors explicitly.

A styled discount label does not create a Shopify discount. A button labeled “Subscribe” does not by itself select a valid selling plan. Ask for the design and commerce configuration separately, and verify the purchase in the cart or checkout.

## Copy-ready examples

### Create a page from a brief

> Build a product-focused landing page for the attached product and ad. The audience is [audience], and the main action is [action]. Use the approved benefits and product facts in the attached brief. Include a hero, product education, existing reviews, a Buy Box, and an FAQ only where they support the brief. Do not invent testimonials, product claims, discounts, or scarcity. Keep the page responsive.

### Change one section

> Edit only the selected hero section. Put the image beside the copy on desktop and keep the existing mobile stack. Preserve the text, product, CTA destination, and all sections below the hero. The result should have no horizontal overflow and the primary button should remain visible without overlapping the image.

### Use desktop and mobile Figma references

> Use these as two responsive versions of the same page: Desktop: [frame link]. Mobile: [frame link]. Match their section order, spacing, typography, and media placement as closely as possible. Use the attached real products for purchase actions. Do not interpret the mobile frame as a second independent page.

### Redesign a Buy Box without changing commerce

> Update the selected Buy Box's appearance to match the reference. Preserve the product IDs, available variants, default purchase selection, selling plans, quantities, discount application, and add-to-cart behavior. Do not replace working commerce controls with static buttons. I will test every purchase option after the edit.

### Reuse an approved section

> Work from the approved section I inserted from Saved Sections. Change only its headline, image, and supporting copy using the supplied assets. Preserve its layout and existing button behavior. Do not rebuild it as a new section.

For a Global Section, decide whether the edit should affect the shared source. [Detach it](/build/global-sections) first when only this page should change.

### Correct a specific mismatch

> In the mobile hero, the product is cropped at the top. Keep the copy and section height unchanged; adjust only the image position so the full product is visible. Preserve the desktop crop. Do not replace the image.

### Change a shopper action intentionally

> Change the selected CTA to open [full destination URL] instead of adding to cart. Keep its appearance and label unchanged. Do not modify the Buy Box or other buttons. I will verify the destination from the final live page.

## Make responsive instructions explicit

The editor's base/mobile mode is **Editing All Sizes**, while desktop can have its own overrides. State the desired mobile and desktop outcomes in your prompt and inspect both after the edit. “Mobile only” in the request is a constraint to verify, not a reason to skip checking desktop.

## Iterate without losing control

Review one meaningful change before stacking another request on top of it. If the result is wrong, name the mismatch and the parts that were correct. For example: “The new spacing is right, but the CTA action changed. Keep the spacing and restore the original cart action.”

Use [Undo/redo](/build/undo-redo) when appropriate. Use Chat history to resume a discussion, not to restore an old page version. Save a tested draft or publish deliberately after reviewing the result.

## Avoid these requests

“Make it convert better,” “fix everything,” and “make it like this” leave the scope unclear. Replace them with a target, a reference, and the specific result you need.

Do not paste private API keys or account credentials into prompts. Do not ask the assistant to fabricate customer reviews or unsupported product claims. Supply approved source material instead.
